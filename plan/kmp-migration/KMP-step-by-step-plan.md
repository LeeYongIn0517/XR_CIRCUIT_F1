## 1. 목표와 변경된 전제

데이터 모델과 비즈니스 동작은 Kotlin Multiplatform으로 공유하고, UI는 플랫폼에 맞게 분리한다.

- Android 스마트폰: Jetpack Compose + **2D 트랙 이미지**.
- iOS 스마트폰: SwiftUI + **2D 트랙 이미지**.
- Android XR: 기존 Jetpack XR / SceneCore + **3D 트랙** 유지.
- 스마트폰에는 3D 엔진이나 GLB→USDZ 변환을 도입하지 않는다.
- 서킷 정보·API·캐시·선택 상태는 공유하고, 그림을 그리는 방식과 리소스 로딩은 플랫폼별로 구현한다.

이 계획은 기존 `KMP-review.md`의 **스마트폰 3D 이식 전제를 대체한다.** 이전 문서는 초기 검토 기록이며, 이후 작업 범위는 이 계획을 우선한다. 기존 분석은 정적 검토로, 빌드·실기기 검증은 아직 수행하지 않았다.

### 기능 유지 원칙

기본안은 **트랙 이미지 + 섹터/DRS 투명 레이어 + 2D 경로 좌표**다. 기존에 동작하는 섹터/DRS 토글과 차량 마커 루프를 2D에서도 유지하기 위한 안이다. 이미지 한 장만 표시하는 축소안은 1단계에서 사용자가 선택할 수 있다. 단순 이미지 사용을 기존 상호작용 제거에 대한 승인으로 해석하지 않는다.

현재 미구현으로 확인된 출발 그리드 데이터 연동, 전략 데이터, 뷰 리셋, Pins의 실제 표시 기능은 이번 리팩토링에서 자동으로 신규 개발하지 않는다. 1단계에서 현재 상태를 재확인하고, 추가를 원하면 별도 범위로 기록한다. 45초 마커 루프는 시각적 애니메이션이며 실시간 레이스 데이터가 아니다.

## 2. 단계별 실행 규칙

1. **사용자가 지정한 단계 하나만 실행한다.** 예: “3단계만 실행해줘.”
2. 실행 전 이전 단계의 완료·검토 기록, 현재 Git 상태, 적용되는 프로젝트 지침을 확인한다.
3. 해당 단계 안의 필요한 구현과 검증은 수행하되, 다음 단계로 자동 진행하지 않는다.
4. 단계 종료 시 변경 내용·검증 결과·남은 문제·사용자 확인 항목을 보고하고 멈춘다.
5. 사용자가 다음 단계 실행을 지시하면 진행한다. 사용자가 앞 단계 수정을 요청하면 해당 수정만 수행하고 다시 보고한다.
6. 사용자 작업을 덮어쓰지 않는다. 새 브랜치 또는 기존 작업 브랜치 사용은 실제 저장소 상태에 맞춰 정하고 보고한다. 커밋·원격 푸시·PR 생성은 요청 범위에 따라 수행한다.
7. 검증하지 못한 항목은 통과로 표시하지 않는다. 실기기·서명·계정 문제는 `사용자 확인 필요` 또는 `차단됨`으로 기록한다.
8. 승인된 단계의 완료 기준을 바꾸거나 기능을 제거해야 하면 변경안을 제시하고 해당 변경 작업을 멈춘다. 영향 없는 작업은 완료한다.
9. 테스트 트랙 업로드와 프로덕션 출시는 별도 단계로 분리한다. “빌드해줘”를 “배포해줘”로 해석하지 않는다.

## 3. 목표 구조

아래는 논리 구조다. 필요 이상으로 Gradle 모듈을 늘리지 않으며 실제 모듈 이름은 2단계에서 확정한다.

```text
공통 Kotlin
  domain: 모델 / Repository 계약 / UseCase
  data: DTO / 매퍼 / API / 캐시 / Repository 구현
  shared: CircuitStore / 앱 조립 / iOS 공개 facade
  track: 순수 경로 보간 / 재생 상태

플랫폼 어댑터
  Android: HTTP 엔진 / assets / 앱 수명주기
  iOS: HTTP 엔진 / bundle / Swift 관찰·취소 연결

플랫폼 UI
  presentation-mobile: Compose / 2D 그림·오버레이
  presentation-xr: Jetpack XR / 기존 3D 모델
  iosApp: SwiftUI / 2D 그림·오버레이

앱 산출물
  Android mobile release
  Android XR release
  iOS archive
```

Android와 XR는 같은 Android용 공유 코어를 사용한다. 별도의 XR KMP 컴파일 타깃을 만들지 않는다. Android flavor는 앱 모듈에 두며, iOS 공개 API에는 Android 리소스 ID·Compose Color·XR Vector3를 노출하지 않는다.

- [ ] 심사 대기·승인·공개 상태를 구분해 보고한다. 심사 제출을 출시 완료로 표현하지 않는다.
- [ ] 출시 후 문제 발생 시 배포 중단·이전 정상 코드 기반 수정 릴리스 절차를 준비한다. 앱스토어의 임의 다운그레이드가 가능하다고 가정하지 않는다.

**산출물:** 제출/출시 기록, 실제 공개 상태, 운영·복구 안내.

**완료 기준:** 사용자 지시 범위의 제출/공개가 확인된다. 장기 심사 대기 감시가 필요하면 별도 요청에 따라 설정한다.

**사용자 확인:** 플랫폼별 실제 공개 상태와 운영·복구 안내를 확인한다.

**실행 지시문:**

> 10단계 결과를 확인했어. [플랫폼]의 [버전]에 대해 [심사 제출만 / 승인 후 수동 공개 / 지정한 출시 방식]으로 11단계를 실행해줘.

## 5. 모든 단계에서 사용할 결과 보고 형식

```markdown
### N단계 결과
- 상태: 검토 대기 / 수정 필요 / 차단됨
- 기준 커밋 및 작업 브랜치:
- 이번 단계에서 변경한 내용:
- 주요 변경 파일:
- 검증한 명령·환경과 결과:
- 실행하지 못한 검증 및 이유:
- 이전 XR 동작에 미치는 영향:
- 사용자에게 보여줄 화면 또는 산출물:
- 알려진 문제와 다음 단계 영향:
- 사용자 확인 항목:
- 다음 단계: 사용자 지시 대기
```

단계별 상세 기록은 프로젝트의 기존 `plan/` 아래 `kmp-migration/` 같은 전용 폴더에 모으는 것을 제안한다. 실제 위치는 1단계에서 기존 문서 구조를 확인해 정한다. 이 계획 원본과 실행 기록의 경로를 결과 보고에 명시하고, 문서를 다른 채팅으로 넘길 때도 현재 승인 단계와 미해결 항목을 함께 전달한다.

## 6. 수정·중단·복구 규칙

- **범위 수정:** “N단계에서 ○○만 수정해줘. 다음 단계는 진행하지 마.”라고 지시한다.
- **일시 중단:** 현재 변경·검증·미완료 항목을 기록하고 멈춘다. 자동으로 작업을 재개하지 않는다.
- **회귀 발생:** 마지막 정상 검증 지점과 비교해 해당 단계의 변경부터 조사한다. 사용자 변경을 포함한 전체 reset/clean은 하지 않는다.
- **복구:** 단계별 커밋이 있으면 선택적 revert를 검토하고, 없으면 해당 단계 diff만 되돌리는 방안을 먼저 제시한다. 이미 배포한 앱은 수정 버전 배포 절차를 따른다.
- **KMP 재판단:** 2~4단계에서 Swift 연결·빌드 유지 비용이 예상보다 크면 원인과 대안을 보고한다. 단순 난관만으로 임의 중단하거나 네이티브 재작성으로 전환하지 않는다.
