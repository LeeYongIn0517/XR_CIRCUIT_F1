# OpenF1 API 적용 계획 — 과거 데이터 → 유료 실시간 전환
## 1. 목표
- **1단계**: 무료 **과거(히스토리컬) REST** 데이터로 UI·도메인 로직을 완성한다.
- **2단계**: **유료 실시간**으로 바꿀 때, UI와 도메인은 최대한 그대로 두고 **데이터 공급 층만 교체**한다.
- 실시간 구현은 **MQTT/WSS(권장)** 또는 **인증된 REST 폴링** 중 선택 가능하되, **동일한 추상화 뒤**에 둔다.
---
## 2. 설계 원칙
### 2.1 단일 도메인 모델
- OpenF1 JSON 필드명·REST/MQTT 페이로드 차이(`_id`, `_key` 등)는 **데이터 소스 경계에서만** 흡수한다.
- 앱 내부(UseCase, ViewModel, XR 레이어)는 **세션·드라이버·위치 샘플·텔레메트리 샘플** 같은 **도메인 타입**만 사용한다.
- 이렇게 하면 “과거 재생”과 “라이브 스트림”이 **같은 렌더링·보간 코드**를 공유한다.
### 2.2 데이터 소스 추상화
역할 이름은 예시이며, 프로젝트 네이밍에 맞게 조정하면 된다.

| 추상화 | 책임 |
|--------|------|
| `OpenF1SessionContext` (또는 동등 개념) | 현재 `meeting_key`, `session_key`, 세션 타입, 시간 범위 |
| `TelemetryFeed` / `CircuitPositionsFeed` (인터페이스) | **위치·카 데이터·(선택) 순위·날씨**를 **시간 순 이벤트** 또는 **스냅샷 스트림**으로 공급 |
| 구현 A: `HistoricalRestTelemetryFeed` | REST로 구간 조회 → 로컬 큐에 적재 → 재생 타이머로 방출 |
| 구현 B: `LiveMqttTelemetryFeed` | MQTT/WSS 구독 → 메시지 파싱 → 동일 도메인 이벤트로 방출 |
| 구현 C: `LiveRestPollingTelemetryFeed` | Bearer 토큰으로 주기적 GET → 최신 구간만 병합 → 동일 이벤트로 방출 |
UI는 **어떤 구현인지 모른 채** `TelemetryFeed`만 구독한다.
### 2.3 모드 명시
- **Replay**(과거): 시작 시점·배속·일시정지를 앱이 제어한다.
- **Live**(유료): 서버 시계 기준; 일시정지는 “표시만 멈춤” 수준으로 제한할지 정책으로 분리한다.
  모드는 빌드 플래그만이 아니라 **런타임 설정**(디버그 메뉴, 구독 여부)과 연결할 수 있게 두면 전환 테스트가 쉽다.

## 3. 계층 구조 (권장)
Presentation (Compose / XR) ↑ ViewModel / SessionController ← 재생 상태, 카메라, 선택 드라이버 ↑ UseCase "Observe circuit state" ← 단일 진입점 ↑ TelemetryFeed (interface) ← 위치·속도 등 통합 스트림 ↑ HistoricalRest… | LiveMqtt… | LiveRestPolling… ↑ Retrofit / MQTT Client / OkHttp

- **Retrofit**: 히스토리컬 REST + (실시간 시) 폴링용 REST 공통.
- **MQTT**: 실시간 전용 클라이언트는 별 모듈 또는 별 DI 바인딩으로 두어, 무료 빌드에서 제외하기 쉽게 한다.
---
## 4. REST 폴링 vs MQTT/WSS 선택 가이드
| 항목 | 인증 REST 폴링 | MQTT / WSS |
|------|----------------|------------|
| 구현 난이도 | 기존 Retrofit 확장으로 단순 | 브로커·재연결·토픽 설계 필요 |
| 트래픽·배터리 | 짧은 주기 폴링 시 부담 | 푸시라 유리 |
| 지연 | 폴링 간격에 묶임 | 상대적으로 낮음 |
| 권장 | 프로토타입·백업 경로 | 문서상 라이브 **권장** 경로 |
**권장 전략**: 인터페이스 하나에 두 구현을 모두 두고, 실서비스는 MQTT를 기본으로 하고 REST 폴링은 폴백·간단 기기용으로 유지할 수 있다.
---
## 5. 인증·보안 (실시간 전환 시)
- OAuth2 토큰 발급(`POST /token`)은 **가능하면 백엔드**에서만 수행하고, 앱에는 **단기 토큰 또는 자체 세션**만 전달하는 패턴이 문서 권장과 맞다.
- 앱이 직접 MQTT에 붙는 경우에도 **비밀번호는 앱에 하드코딩하지 않는다.**
  이 문서는 코드가 아니라 **경계**만 정의한다. 구체 저장소는 보안 요구에 맞게 선택한다.
---
## 6. 히스토리컬 → 라이브 전환 시 바꾸는 곳 (체크리스트)
- [ ] `TelemetryFeed` 구현체 바인딩만 `Historical*` → `Live*` 로 교체 (Hilt 등).
- [ ] `session_key=latest` 사용 여부·세션 종료 감지 로직 추가.
- [ ] 실시간 MQTT 페이로드의 `_id` / `_key` 처리(중복·갱신 병합)를 **매퍼**에 한정.
- [ ] 토큰 만료(약 1시간) 시 재발급 루프.
- [ ] 레이트 리밋·에러 시 백오프(실시간 REST 폴링 시 특히 중요).
  **바꾸지 않는 것**: 도메인 모델, 트랙 좌표 정규화, 마커 보간, UI 상태 머신.

## 7. 테스트 전략
### Replay 피드스 + JSON fixture / 짧은 녹화
- **Replay 피드**: 앱 입장에서는 “라이브처럼 보이지만”, 실제로는 과거 세션 데이터를 시간 순으로 다시 흘리는 쪽(히스토리컬 REST로 받아서 재생하는 TelemetryFeed 구현).
- **JSON fixture**: 네트워크 없이 테스트할 수 있게, API 응답을 파일로 저장해 둔 샘플 데이터 (예: location_sample.json). 테스트 코드가 이걸 읽어서 피드가 주는 것처럼 넣으면 ViewModel/UI 동작을 재현 가능하게 검증할 수 있음.
- **짧은 구간 녹화**: 실제 API에서 몇 초~몇 분치만 받아서 파일로 저장해 두고, 그걸 replay 피드에 꽂아서 테스트하는 방식. fixture보다 실제에 가깝고, 전체 레이스를 받을 필요는 없음.

### Live 피드 + 인터페이스 모킹 + CI에서는 선택적으로
- **Live 피드**: 유료 실시간(MQTT나 인증 REST)으로 붙는 구현.
- **인터페이스 모킹**: TelemetryFeed 같은 인터페이스를 테스트에서 가짜 구현으로 바꿔서, “MQTT가 이런 메시지를 보냈다”처럼 원하는 데이터만 흘려보내는 것. 그러면 실제 OpenF1·브로커에 연결하지 않고도 같은 ViewModel/UI 테스트를 그대로 돌릴 수 있음.
- **통합 테스트는 구독·세션 시간에 의존**: 통합 테스트는 “진짜 API/MQTT에 한 번 붙어서” 끝까지 검증하는 테스트인데,
유료 구독 계정이 있어야 하고,
레이스/세션이 돌아가는 시간에만 의미 있는 데이터가 나오며,
네트워크/서버 상태에 따라 오늘은 되고 내일은 실패할 수 있음.
그래서 매번 CI에서 필수로 돌리기 어렵다는 뜻입니다.
- **CI에서는 선택적으로만**: 자동 빌드 파이프라인에서는 보통 fixture/모킹 테스트만 돌리고, “실제 브로커에 붙는 통합 테스트”는 수동·스테이징·주말에만 같은 식으로 선택하라는 권장입니다.

---
## 8. 요약
과거 데이터 단계에서는 **REST만**으로 충분하고, 유료 실시간으로 넘어갈 때 **MQTT/WSS 또는 인증 REST 폴링을 “같은 `TelemetryFeed` 구현 뒤”에 붙이면** 전환 비용을 최소화할 수 있다. 핵심은 **도메인·UI와 전송 방식의 분리**, 그리고 **재생 모드와 라이브 모드의 명시적 분리**다
